# Ошибка Permission denied при подготовке материалов

## Содержание документа

Диагностика и восстановление доступа к рабочему хранилищу в закрытом контуре. Пример — отказ создания `/data/cache/vision/tmp…` из фотографий серверной ошибки. Исправление данных можно применить с уже установленным образом приложения; скачивать модели не требуется.

## Контекст

Ошибка актуальна для `main` до исправления, база `25709de`: `Storage.put` создавал временный файл в каталоге кэша после вычисления результата, а `doctor` проверял доступность только корня. Доступный корень не гарантирует возможность записи в `cache/vision` или другой вложенный каталог.

Фотографии подтверждают EACCES при записи. Фактические UID/GID, ACL и режим монтирования сервера по ним установить нельзя. Неподходящий владелец после переноса, запуск через другого пользователя или `sudo` — возможные причины, а не установленный паспорт сервера.

## Симптомы и задачи

- Подготовка завершается `[Errno 13] Permission denied: '/data/cache/vision/tmp…'`.
- HTTP `/health` и опрос состояния могут отвечать 200: это не подтверждение записи в кэш.
- На хосте `storage/` доступен, но отдельные вложенные каталоги принадлежат другому числовому UID.

Исправление проверяет существующие вложенные данные при старте приложения, до открытия базы и запуска Processor. Промах кэша проверяет место записи до вызова модели. Ошибка во время HTTP-операции с хранилищем возвращает 503 с кодом `storage_unwritable`, UID/GID, путём и request ID. Отказ записи не подменяется успешным результатом; готовый кэш не удаляется.

## Подготовка

Работайте из каталога установленного сервиса, где лежат `compose.yaml`, `.env` и `Makefile`, от того пользователя, который будет выполнять `make start`. Нужны существующий локальный образ app и доступ к Docker. Установка должна использовать отдельный bind-каталог `/data`; модели располагаются отдельно.

Перед изменением владельца остановите всех писателей и сделайте полный бэкап фактического `RAPPORTEUR_STORAGE`, включая ACL/права, а также `.env`. Если обычный пользователь не может прочитать каталог, бэкап выполняет администратор. Не изменяйте хранилище вручную во время восстановления и не запускайте на нём другие установки.

Пример бэкапа после остановки, **замените путь на фактический источник `/data` из конфигурации Compose**:

```bash
make down
RAP_DATA_DIR=/srv/rapporteur/storage
mkdir -p "$HOME/rapporteur-backups"
sudo tar --acls --xattrs --numeric-owner -cpf \
  "$HOME/rapporteur-backups/storage-before-permissions-$(date +%Y%m%d-%H%M%S).tar" \
  -C "$RAP_DATA_DIR" .
cp .env "$HOME/rapporteur-backups/env-before-permissions"
```

## Порядок действий

### В обновлённом исходном репозитории или полном комплекте

```bash
make storage-check
make storage-repair
make start
```

Первая команда при исходной неисправности завершится ошибкой и покажет проблемный путь и числовые идентификаторы. `storage-repair` останавливает app/app-shared и оба варианта ASR, меняет владельца и добавляет владельцу необходимые права только у управляемых данных, затем проверяет доступ от UID/GID приложения. Свою или внешнюю Ollama команда не останавливает. Приложение запускается отдельно через `make start`.

### Автономное исправление старой офлайн-установки

Для сервера без обновления образа подготовлен небольшой архив `rapporteur-storage-permissions-2026-11-18.tar.gz`. Он содержит два текстовых инструмента, инструкцию и SHA-256; образы, модели, настройки и рабочие данные отсутствуют. Распакуйте **в корень существующей установки**:

```bash
tar -xzf /путь/к/rapporteur-storage-permissions-2026-11-18.tar.gz
sha256sum -c STORAGE-PERMISSIONS.SHA256SUMS
make down
# Выполните резервное копирование, описанное выше.
bash scripts/storage-access.sh check
bash scripts/storage-access.sh repair
bash scripts/storage-access.sh check
make start
```

Ожидаемый отказ первой проверки не мешает следующей команде; запускайте их последовательно, а не цепочкой с `&&`. Инструмент использует Python из уже загруженного app-образа с `--pull never` и `--network none`. Он работает и со старым образом без нового Python-модуля.

Не запускайте обычный `sudo make …`: тогда UID запуска станет 0. Если для Docker необходим `sudo`, передайте целевую личность явно, например:

```bash
sudo env HOST_UID="$(id -u)" HOST_GID="$(id -g)" \
  bash scripts/storage-access.sh repair
```

Для последующего запуска используйте ту же числовую личность. В штатном сценарии `make` экспортирует UID/GID текущего пользователя; прямой Compose без этих значений может запустить процесс с другим UID.

### Что делает восстановление

Меняются владелец и права корня, управляемых `blobs`, `cache`, `slides`, `pages`, `reports`, `report-templates`, `tmp`, базы `rapporteur.db`, её WAL/SHM/journal и версионных бэкапов. Файлам добавляются права владельца на чтение/запись, каталогам также на проход. Содержимое файлов сохраняется, режим 777 не назначается, неизвестные файлы администратора не переписываются.

Команда отказывается работать при пересечении настроенных каталогов моделей и данных, вложенных монтированиях, символических и жёстких ссылках, неподходящем корне. Для обхода используются дескрипторы каталогов и `O_NOFOLLOW`; перед изменением повторно проверяется тип объекта. Это не замена остановке всех писателей: для восстановления нужен эксклюзивный доступ доверенного администратора.

## Проверка результата

После успешного `check` и `make start` повторите «Подготовить доклады» / «Подготовить заново». Ранее записанные части кэша используются повторно. Результат, который успел вычислиться, но не был записан из-за EACCES, придётся вычислить ещё раз.

Локальная проверка 18 ноября 2026: воспроизведён отказ старого main-образа на `/data/cache/vision` с владельцем 0:0 и процессом 1000:1000. Диагностика отвергла каталог, восстановление исправило доступ, после него работают старый и новый образы. SHA-256 существующих файлов базы, её бэкапов и кэша до/после восстановления совпали. Внешний файл-маркер модели не изменился; настоящие веса и рабочие контейнеры не использовались для ремонта.

Прошли 381 Python-тест без пропусков, Ruff/format/mypy, 36 frontend-тестов, ESLint/TypeScript/Vite и сборка app. Регрессии покрывают отказ до вызова модели, раннюю проверку вложенного каталога, сохранность атомарной записи, живую проверку при исчезновении временного файла, настоящий маршрут загрузки с 503, границы ремонта и поставку инструмента в офлайн-комплекте. Проверки выполнялись в Docker без сети; вызовы Qwen и ASR для этой ошибки не нужны. Локальные журналы: `.local/storage-permissions-2026-11-18/`.

## Диагностика и обращение за помощью

Если после выравнивания UID/GID отказ остаётся, администратору нужны `id`, `ls -ldn` проблемного каталога и его родителей, ACL (`getfacl`), параметры монтирования (`findmnt`) и UID процесса контейнера. Проверьте режим read-only, NFS/root-squash и действующие политики мандатного доступа. Не отключайте защиту системы ради запуска приложения. Локальный тест не подтверждает настройки файловой системы и политик целевого сервера.

## Откат

Восстановление не удаляет данные и не меняет схему базы. При ошибочно выбранном пользователе остановите писателей и повторите процедуру с правильными UID/GID. Для полного возврата владельцев/ACL используйте сохранённый бэкап при остановленном приложении. Сам по себе запуск прежнего образа права обратно не меняет.
