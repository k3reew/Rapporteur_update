# «Репортёр»: передача разработки в новый чат

## Содержание документа

Контекст владельца, устройство сервиса, состояние совместной разработки, исправления аудита 18 ноября 2026, команды, ограничения проверок и следующие задачи. Это точка входа для нового разработчика или нового чата; актуальность сначала сверяется с Git.

## Контекст

### Как начать новый чат

Сопоставь их с handoff; не начинай заново уже выполненные задачи. Сохраняй изменения коллеги и незакоммиченные файлы. Прочитай указанные протоколы перед утверждениями о качестве. Рабочие контейнеры, хранилище и модели не меняй без необходимости задачи. На GitHub не отправляй веса, .env, хранилище, бэкапы и образы. Смена модели чата не требует менять Qwen, Ollama или код приложения. Этот файл переносит инженерный контекст; историю сообщений клиент переносит по своим правилам.

### Зачем нужен сервис

Один оператор готовит справку по конференции для читателя, который не видел её материалы. Можно загрузить доступное сочетание PPTX/PDF, речи DOCX/PDF/TXT, изображений слайдов, аудио и видео. Приложение извлекает текст, использует OCR, при включённом ASR распознаёт речь, предлагает доклады и связи источников. Оператор исправляет реестр, проверяет результаты и выпускает DOCX, Markdown и PDF.

Положения отделов задают интересы организации. Хотя бы одно успешно извлечённое положение требуется до загрузки материалов. После подтверждения докладов отбор определяет, кому нужна полная сводка. Доклад без интереса остаётся в справке карточкой с темой, авторами, организациями и контактами. Неопределённость требует решения оператора. Итоговые рекомендации по фактам сводки — отдельный результат со своей проверкой и актуальностью.

### Принятые ограничения

- Закрытый контур: запуск без внешних API, CDN, скачивания зависимостей и весов на сервере.
- Один сотрудник на рабочем месте; последовательная обработка в одном Processor. Параллельные редакторы сейчас не являются целевым режимом.
- Сохраняются React, TypeScript, Vite, FastAPI, SQLite, Ollama и Whisper. Новая инфраструктура без измеренной потребности не вводится.
- Порты и имена проектов не должны мешать другим установкам. Штатный веб-порт — 18763; Ollama и ASR доступны в Docker-сети.
- Веса, `.env` и рабочее хранилище существующей установки сохраняются. В Git их нет.
- Пользователь предпочитает самостоятельную работу без повторных согласований уже разрешённых действий. Переписывание чужой истории и уничтожение данных не разрешены.
- Статья требует фактических результатов, отрицательные результаты не скрываются. Авторские сведения владелец заполняет сам.

### Что реализовано до этого прохода

- Четыре этапа интерфейса: материалы → доклады → проверка → справка; светлая, тёмная и системная темы.
- Частичные ошибки загрузки по файлам, папки, ручные привязки, страницы и границы записей, разделение и объединение докладов.
- Ограниченные структурированные задачи, перечисление допустимых идентификаторов, порции длинных входов, компактный повтор обрыва и кэш успешных частей.
- Извлечение фактов, буквальная сверка цитат, проверки чисел и источников, смысловой критик и оценка понятности новому читателю.
- Проверка отдельного доклада, переход к следующему, массовое подтверждение только допустимых результатов.
- Версионный отбор по положениям отделов, ручные решения, устаревание результатов после изменения оснований.
- Сохраняемые report_jobs, снимок входа и шаблона, SHA-256, идемпотентность, восстановление после перезапуска и максимум одна версия на задание.
- Старый синхронный endpoint выпуска и скачивание старых справок сохранены.

Коллега добавил карточки авторов/организаций/контактов, промпты v4 и `summary.yaml`, режимы ASR `auto/off/cpu/gpu`. Текущая политика из `summary.yaml` — 6–10 предложений основного текста и отдельные выводы. Файл задаёт диапазон явно; не полагайтесь на исторические 4–5 из описаний ранних профилей. Без интереса отделов доклад получает только карточку и может войти в справку. Штатная загружаемая модель Whisper теперь small; уже установленные large-v3 остаются совместимыми.

### Архитектура и точки входа

| Область | Реализация |
| --- | --- |
| Браузер | `frontend/src/`, каркас App, Preparation, Processing, SummaryView, ReportPanel; общий api и useResource |
| HTTP / жизненный цикл | `src/rapporteur/app.py`, маршруты по областям в `api/` |
| Данные | `db.py`, SQLite, читающие снимки и отдельные транзакции записи; файлы через Storage |
| Подготовка | `preparation.py`, извлечение в `ingest/`, кэш подготовленных фрагментов |
| Очередь | `processing.py` и Processor: подготовка, отбор, обработка докладов, выпуски |
| Отделы | `departments.py`, `screening.py`, `interest.py`, рекомендации и ревизии оснований |
| LLM | `llm/`, Ollama `/api/chat`, profiles.yaml, prompts/, summary.yaml |
| Факты и сводки | `summarize/`: пакет, факты, проверка цитат, смысловой критик и итоговый выбор |
| Справка | `reports.py`, report_jobs.py, `report/`, templates/starter/report.docx |
| ASR | `asr_service.py`, `asr_models.py`, Whisper/CTranslate2 и ffmpeg; внутренний HTTP |
| Поставка | Dockerfile, compose.yaml, Makefile, scripts/doctor.sh, scripts/asr-mode.sh |

Три логических runtime-сервиса — app, Ollama, ASR. ASR необязателен, CPU/GPU представлены альтернативными профилями Compose. `app-shared` использует внешнюю Ollama: задаются `OLLAMA_NETWORK` и `OLLAMA_URL`. При этом `OLLAMA_MODELS_DIR` по-прежнему должен указывать на локальные manifests/blobs для проверки и паспорта весов; профиль server требует 27B. Порядок подключения — в [руководстве Ollama](docs/ollama.md).

Материал и доклад — разные сущности. Фрагмент принадлежит исходному файлу и локатору, один источник может связываться с несколькими докладами. Сводка опирается на утверждения, утверждения — на цитаты и локаторы. Буквальное совпадение цитаты само по себе не доказывает смысловую подтверждённость.

Длительные вызовы моделей выполняются вне транзакций. Версии входов защищают от публикации устаревших результатов. Файлы записываются атомарно; ключи кэша включают содержание, параметры и версии этапов. Не следует «чинить» проблему удалением всех кэшей или ослаблением проверки доказательств.

### API и навигация

Префикс — `/api/v1`. Полный контракт: [docs/api.md](docs/api.md) и [OpenAPI](docs/api-openapi.json).

- `/conferences`, `/conferences/{id}/materials`, `/conferences/{id}/preparation` — конференции, загрузка, предложение и подтверждение реестра.
- `/talks/{id}` — ручная карточка с `revision`; preparation использует свой `version`.
- `/conferences/{id}/screening`, `/talks/{id}/screening` — получение/пересчёт отбора и ручное решение с версией.
- `/conferences/{id}/processing`, `/conferences/{id}/progress`, `/talks/{id}/retry` — запуск, опрос и повтор.
- `/talks/{id}/summary` и `/talks/{id}/summary/review`, массовая проверка `/conferences/{id}/summaries/review` — просмотр, правка и подтверждение.
- `/departments`, `/talks/{id}/recommendations` — положения и основания интереса.
- `/conferences/{id}/report-jobs`, `/report-jobs/{id}`, `/report-jobs/{id}/retry` — фоновый выпуск и повтор.
- `/conferences/{id}/reports`, `/report-versions/{id}/files/{format}` — версии и скачивание.
- `/system`, `/model` — состояние и профиль модели.

Адреса этапов конференции заканчиваются на `materials`, `talks`, `review`, `report`. Старый `processing` ведёт к проверке. Прямые ссылки на доклад сохранены. Опрос обычно каждые 5 секунд; переход и перезагрузка восстанавливают серверное состояние, черновики защищены от случайного ухода.

| Ошибка | Решение и регрессия |
| --- | --- |
| Подтверждение подготовки затирало ручную карточку | Синхронизация карточки/предложения и версии в одной транзакции; подтверждённое представление берёт поля реестра; тесты card и upgrade |
| Старый локально изменённый черновик мог обойти защиту | Данные миграции v5 один раз повышают версии существующих preparations; старые запросы получают 409 до записи |
| Изменение карточки во время подготовки публиковало старый снимок | Повышение версии и повторная постановка подготовки; worker отбрасывает старый результат |
| Полная страница определения переполняла критик | Окна вокруг определения и цитат, порции с сохранением IDs, общий контекст понятности; tests/test_summary_v3.py |
| Большой max_tokens пользовательского профиля делал бюджет отрицательным | Ограниченный резерв именно критика; тест профиля 16k/8k |

| DOCX/TXT внутри папки оставались без авторов | Извлечение недостающего авторства при сохранении заполненной карточки; tests/test_card.py |
| Новый шаблон терял строку неизвестного автора | Общая подстановка «Автор не установлен», проверка старого и нового шаблонов во всех форматах |
| Смена Whisper смешивала config и веса | Полная проверенная ревизия, атомарный active.json, прежние файлы сохраняются |
| Новая ревизия могла получить текст от старого загруженного ASR | Один снимок ревизии для запроса/ключа; несовпадающая ревизия ответа не попадает в кэш |
| Повторная сборка бандла оставляла старый active.json | Точная копия управляемого поддерева ASR через staging с откатом |
| Повторно используемая ревизия принимала посторонний model config | Проверка точного состава файлов до активации |
| Для card_only показывалась готовая сводка | «Карточка готова», сводка не открывается; frontend regression |
| Карта документации отстала от реализации | Регистрация протоколов и handoff, актуализация описаний и хэшей |

Точные имена тестов, результаты и условия находятся в [протоколе исправлений](docs/benchmarks/2026-11-18-audit-fixes.md). [Исторический аудит](docs/benchmarks/2026-11-18-summary-card-audit.md) сохранён без переписывания результатов.

Ограничения поведения: происхождение каждого поля карточки отдельно не хранится. Намеренно пустые авторы при повторной подготовке могут быть заполнены из источника. Объём опор одного предложения всё ещё может превысить контекст модели: тогда возвращается явная контролируемая ошибка, доказательства молча не удаляются.

### Отказ доступа на закрытом сервере

После сведения main владелец прислал фотографии `PermissionError: [Errno 13]` при записи `/data/cache/vision/tmp…`. Ошибка актуальна на main `25709de`; точный владелец и ACL сервера неизвестны. Воспроизведён вариант: каталог 0:0, процесс 1000:1000. Исправление `fix/storage-permissions` добавляет проверку вложенных данных до старта Processor и до вычисления отсутствующего кэша, понятный HTTP 503, очистку незавершённой атомарной записи и автономную команду восстановления.

[Инструкция](docs/storage-permissions.md) описывает `make storage-check`, `make storage-repair` и небольшой комплект для прежнего app-образа. Источник /data берётся из нормализованной Compose-конфигурации. Восстановление запрещено при пересечении с моделями, вложенных монтированиях и ссылках. Оно работает только с управляемыми данными и требует остановки всех писателей; само содержимое файлов не меняет. Подготовка после ремонта повторяется кнопкой, готовые части кэша сохраняются.

Свежая проверка: 381 Python-тест, 36 frontend-тестов, линтеры/типы/сборка app; Docker-проверка отказа, ранней диагностики, ремонта и запуска обоих образов. SHA существующих файлов сохранены. Это проверка файловой системы, Qwen/A100 и речь заново не оценивались. Локальные результаты — `.local/storage-permissions-2026-11-18/`; автономный архив — `/home/kirill/Documents/Rapporteur-storage-permissions-2026-11-18/rapporteur-storage-permissions-2026-11-18.tar.gz`. Архив содержит только инструменты и инструкцию, не образы или веса.

### Состояние проверок

Для прежнего аудита полный Python-набор: 360 passed, без пропусков; Ruff/format/mypy прошли. Фронтенд: 36 тестов, ESLint/TypeScript/Vite прошли. Сборка app, OpenAPI и обновление копии старой базы проверены. Журналы и прочие результаты — в протоколе исправлений. Предыдущий аудит на `f4fd5df` имел 338 Python-тестов; не смешивайте эти запуски.

Сквозной HTTP-сценарий завершён: оба автора, сохранение ручного контакта и конфликт версии, одна сводка `ready` из 6 предложений с 8 успешными проверками, одна карточка, одна версия трёх форматов и идемпотентность. Для отрицательного доклада после невалидных ответов 4B потребовался один ручной выбор «Только карточка». Две записи одинакового положения остались после повторной настройки стенда. Проверка перезапуска сохранила задания и хэши экспортов. В браузере проверены конфликт, источник, подпись карточки и восстановление страницы.

Локальное оборудование: Ryzen 5 3600, около 15 GiB доступной RAM, RTX 2060 6 GiB. При наблюдении текущего Qwen 4B Ollama `/api/ps` сообщал `size_vram=0`: присутствие GPU не означает, что этот проход выполнялся на ней. В журнале Ollama есть `failed to initialize CUDA: no CUDA-capable device is detected`; рабочая Ollama в ходе проверки не перенастраивалась. Сквозной инженерный сценарий использует Qwen3.5 4B Q4_K_M, v4, контекст 16384, максимум 4096 токенов, temperature 0.1, reasoning=false. Это не оценка качества на корпусе конференций.

Целевой сервер по данным владельца: 2× Xeon Gold 6346, 512 ГБ RAM, отдельные SSD/HDD RAID-массивы и 2× A100 40 ГБ. Docker Compose и NVIDIA Container Toolkit установлены. Планируется Qwen3.5 27B; активная конфигурация сервера и её качество этим проходом не подтверждены. GPU используются независимо.

### Команды разработки и проверки

```bash
git status --short
git branch --show-current
git log --oneline -8
git ls-remote --heads origin main feat/summary-and-card codex/fix-summary-card-audit

```

`make check` использует Docker и может собирать dev-образы. Для проверки без сети на этой машине доступны `rapporteur-dev:local` и `rapporteur-web-dev:local`:

```bash
docker run --rm --network none --user 1000:1000 -e PYTHONPATH=/app \
  -v /usr/bin/make:/usr/bin/make:ro -v "$PWD:/app" -w /app \
  rapporteur-dev:local sh -c \
  'ruff check . && ruff format --check . && mypy && pytest -o addopts="" -q -ra'

docker run --rm --network none --user 1000:1000 \
  -v "$PWD/frontend:/app/frontend" -w /app/frontend \
  rapporteur-web-dev:local sh -c \
  'eslint . && tsc -p tsconfig.json && vitest run && vite build --outDir /tmp/dist --emptyOutDir'
```

Монтирование make позволяет выполнить тесты команд запуска: в прежнем Python dev-образе этой программы нет. Это локальный способ проверки, не требование к серверу. Значения UID/GID при необходимости заменяются своими.

Инструмент документации на этой машине расположен вне репозитория:

```bash
python3 /home/kirill/.agents/skills/codebase-analysis-ai/scripts/codebase_analysis_ai.py --root "$PWD" check
```

Не устанавливайте хуки/CI автоматически. Свежесть карты обновляется после содержательной сверки документов, а не вместо неё. Если GitHub CLI/обычный push недоступен, подключённый GitHub-плагин умеет публиковать дерево и открывать PR; после публикации нужно сравнить Git tree SHA, получить коммит локально и проверить чистоту ветки. Не извлекайте токены из клиента.

### Запуск, обновление и откат

На сервере с уже установленными образами и весами:

```bash
make config
make doctor
make start
make ps
```

`make start` использует `--no-build --pull never`. `ASR_MODE=auto` выбирает GPU-ASR при двух и более строках устройств в `nvidia-smi -L`, иначе выключает его; `doctor` отдельно проверяет заданные UUID/номера и их различие; CPU задаётся явно. Меняйте режим через make, поскольку прямой compose up не останавливает неактивные варианты.

Перед обновлением остановите установку и сохраните полный том, `.env`, старые образы и конфигурацию. Пример ниже предполагает `RAPPORTEUR_STORAGE=/srv/rapporteur/storage`. Если `.env` указывает другой путь, архивируйте фактический рабочий каталог. Полный порядок [обновления](docs/offline.md#обновление-существующей-установки) и [отката](docs/offline.md#откат) включает установку комплекта и восстановление предыдущих образов:

```bash
cd /srv/rapporteur
make down
mkdir -p "$HOME/rapporteur-backups"
tar --acls --xattrs -czf "$HOME/rapporteur-backups/storage-before-update.tar.gz" \
  -C /srv/rapporteur storage
cp .env "$HOME/rapporteur-backups/env-before-update"
```

У нового комплекта сохраните абсолютные пути прежних моделей и рабочего тома. Одно хранилище обслуживает одна версия app. SQLite создаёт копии базы перед миграциями, но это не заменяет полный бэкап файлов. Откат выполняется старым образом и восстановлением всего хранилища из согласованного бэкапа, не запуском старого кода на новой базе.

Веса Whisper новых загрузок лежат в `revisions/<размер>-<HF commit>/`, `active.json` содержит JSON-строку относительного пути. Старые плоские каталоги работают без указателя. При смене весов остановите app и ASR, переносите весь каталог, затем запустите оба сервиса. Новый формат требует обновлённого ASR-кода; для старого образа сохраните плоский каталог. При несовпадении ревизии ответа и запрошенного снимка app выдаёт ошибку без записи в кэш.

### Следующие задачи и модернизация

1. Синхронизировать работу с коллегой: новые задачи от `origin/main`, PR в `main`; исторические ветки не использовать как вторую основную. Перед обновлением сервера собрать новую проверенную поставку из main.
2. Подтвердить серверный паспорт Qwen/Whisper: SHA весов, квантование, параметры, реальное распределение GPU. Пройти короткую приёмку на A100 и проверить обновление копии серверного хранилища.
3. Получить проблемную презентацию и журналы исходного 502/обрыва. Общие классы ошибок исправлялись, конкретный серверный случай пока не воспроизведён.
4. Утвердить эталон по 16 докладам и повторяемую оценку фактов, отрицаний, чисел, авторства, локаторов и рекомендаций. Для статьи сохранять выходы до ручной правки.
5. Добавить измерения этапов, повторов и причин ошибок по request/job ID, затем выбирать оптимизацию по фактическим затратам.
6. Хранить происхождение ручных и извлечённых полей карточки. Это устранит неоднозначность намеренно пустых значений.
7. Свести версии приложения, моделей, промптов, шаблонов и базы в паспорт поставки.
8. Выносить обработку в отдельный процесс и сравнивать Ollama с другими серверами моделей только при подтверждённой потребности и измерениях на целевой модели. Переход на другую СУБД сейчас не обоснован режимом одного оператора.
